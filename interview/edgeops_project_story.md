# NanoChat-Lab / EdgeOps Copilot 面试话术

## 一句话

我基于 Qwen2.5-1.5B 构建了面向工厂 AMR 运维的本地 Copilot，完成了数据隔离、双 LoRA 专家训练、结构化工具执行、sealed test 和 INT4 验收，并通过一次未晋级的 v3 实验定位了小模型多步规划中的能力迁移问题。

## 30 秒版本

这个项目研究的是：在 4 GB 推理显存目标下，如何让 1.5B 小模型可靠完成设备查询、故障诊断、手册检索和安全拒答。我把系统拆成受控路由、route/tool 与 safety/refusal 两个 LoRA Adapter、JSON Schema 工具状态机、RAG 和 Trace。数据按原文、规范化文本、模板族和 source ID 隔离。最终 v2 sealed test 上，路由准确率 95.55%，工具参数准确率 98.73%，安全拒答 F1 97.84%，JSON 有效率 100%。INT4 峰值显存约 2.13 GiB，但 p95 延迟约 16--17 秒，所以结论是显存可行、延迟仍需优化。

## 1 分钟版本

项目最初只是本地 RAG 和工具调用实验，后来我将场景收敛为工厂 AMR 运维，避免没有业务边界地堆功能。推理链路中，模型只负责语言理解、证据回答和受限规划；工具执行器独立做白名单、参数 Schema、安全等级、重复调用和最大步数校验，运动控制工具不向模型注册。

训练方面，我为 route/tool 和 safety/refusal 分别构建 LoRA Adapter。v2 包含 1.6 万条训练样本、3500 条 dev 和 4000 条 sealed test，四类跨集合重叠均为 0。最终 sealed route/tool 的路由准确率为 95.55%，多步完全匹配率为 79.60%；安全集合保持危险和正常请求各 1000 条，F1 为 97.84%，误拒率为 1.60%。

我还做过一次 v3 多步规划优化。它把 dev `tool_plan` 从 64.0% 提高到 97.2%，但 `fault_diagnosis` 降到 37.6%，整体路由降到 85.6%。因此我没有选择更好看的局部指标，而是拒绝晋级 v3，保留 v2 作为最终版本。

## 3 分钟展开

### 1. 任务和安全边界

系统处理设备状态、资产位置、维护历史、错误码、手册问答和工单草稿。设备状态等事实必须来自工具，手册结论必须有检索证据。移动、急停和保护绕过等高风险动作不进入工具白名单。

### 2. 数据与评测治理

初版评测曾出现接近满分的结果，但进一步审计发现模板重复、集合泄漏和拒答单类评测。我主动废弃这些结果，重新按 source ID 和语义模板族拆分数据。最终 train/dev/sealed test 在原文、规范化文本、模板族和 source ID 上均无交叉。

评测使用模型自由生成，不把无模型规则路由结果当成模型能力。sealed test 只运行一次，只保存聚合结果；打开测试集后不再用于调参。

### 3. 双 Adapter

route/tool Adapter 学习路由、工具选择、参数抽取和多步计划；safety/refusal Adapter 学习危险请求拒绝和正常请求放行。拆分的原因是两类任务目标不同，而且安全误拒与工具准确率需要独立观测。

最终 v2 sealed 指标：

| 指标 | 结果 |
| --- | ---: |
| Route accuracy | 95.55% |
| Tool-name accuracy | 88.93% |
| Tool-argument accuracy | 98.73% |
| Multi-step exact match | 79.60% |
| Safety precision | 98.38% |
| Safety recall | 97.30% |
| Safety F1 | 97.84% |
| False-refusal rate | 1.60% |
| Valid JSON | 100.00% |

### 4. 结构化执行

模型输出 JSON Action 或 `steps`。执行器先验证 action 白名单和参数类型，再检查安全等级、重复调用和最大步数。工具结果与模型文本分离记录到 Trace，模型不能把生成文本直接当成执行成功。

### 5. INT4 结论

NF4 4-bit 权重量化配合 double quantization，在 RTX 2080 Ti 验收中：

- route/tool 峰值显存 2,137 MiB，p95 16.57 秒；
- safety/refusal 峰值显存 2,129 MiB，p95 17.21 秒。

它证明配置满足 4 GB 显存门槛，但没有证明 GTX 1650 上具备同样性能，也没有证明低延迟。高延迟是当前部署短板。

### 6. 失败实验

v2 的 `tool_plan` sealed exact match 只有 54.4%。v3 为此增加了更严格的多步 system contract。局部指标改善明显，但故障诊断和普通工具调用退化，导致整体指标下降。

可能原因包括：

- “用户请求的操作”与故障诊断标签中的隐式两步分解不一致；
- v3 从基座训练新 Adapter，没有从 v2 稳定能力继续微调；
- 1.5B 模型对 system prompt 分布高度敏感；
- token-level eval loss 无法代表严格工具序列正确性；
- 更长 prompt 在 256 token 上限下存在输出截断风险。

这个实验的价值不是产生一个更好的最终模型，而是证明局部优化必须通过全类别回归和晋级门槛约束。

## 常见追问

### 为什么最终选择 v2？

> v2 有完成的数据隔离、dev、sealed test 和 INT4 验收闭环。v3 只在 dev 上改善一个类别，却让整体 route 从 95.35% 降到 85.60%，也没有新的外部 holdout。按照预先定义的门槛，v3 不能晋级。

### DPO 是最终模型吗？

> 不是。DPO 在 checkpoint 50 时偏好准确率已经达到 1.0，继续训练有过拟合风险，而且没有完成 DPO 后自由生成评测。最终安全产物仍是 safety/refusal SFT Adapter。

### 这是模型项目还是规则系统？

> 它是混合系统，但模型指标和规则指标严格分开。LoRA Adapter 负责自由生成的路由、参数和拒答；执行器负责不可绕过的 Schema 与安全边界。sealed 指标来自模型生成，不是硬编码路由结果。

### 为什么不宣称已经在工厂上线？

> 当前证据来自模拟设备网关和固定评测集，没有真实生产工厂部署、长期稳定性或功能安全认证，因此只能表述为工程与评测原型。

### 如果继续优化，优先做什么？

> 从 v2 Adapter 做低学习率增量训练，显式定义复合工作流，并混入旧任务 replay 防止遗忘；提高序列长度，每 25--50 step 做分层生成评测，最后重新构造从未参与调参的 external holdout。不会继续在 v2 sealed test 上选模型。

## 对外表述边界

可以说：

- 完成 v2 双 Adapter 训练、自由生成评测和 sealed test；
- 数据按四类标识实现跨集合零重叠；
- 完成 RTX 2080 Ti 上的 INT4 显存与延迟验收；
- v3 是一次被门槛拒绝的多步规划实验。

不能说：

- 已经在真实工厂或 GTX 1650 上完成最终部署；
- DPO 已经提升安全效果；
- v3 是最终模型；
- 2.13 GiB 显存意味着系统低延迟；
- `tool_plan` 短板已经整体解决。
